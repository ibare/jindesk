# 마이그레이션

앱이 업데이트되면 데이터 파일의 모양이 바뀔 수 있다. 데이터 리포에 이전 판이 남아 있기는 하지만(`DATA.md`의 데이터 리포), 거기서 되살리는 일은 관리자가 손으로 해야 한다. 그래서 마이그레이션은 지금처럼 늘 사본에서 하고, 검증한 뒤 바꿔 끼운다.

## 스키마 버전

- 데이터 폴더 전체에 스키마 버전이 하나 있다(`meta/schema.yaml`의 `schema`). 파일마다 `kind`와 `v`, 블록마다 `type`과 `v`가 있다(`DATA.md`).
- 앱은 자기가 쓰는 스키마 버전 N 과, 1 부터 N 까지의 마이그레이션 단계를 번들에 담는다. 스키마는 `Resources/schemas/<버전>/`에 있다.
- 켤 때 데이터 폴더의 버전을 본다.
  - N 과 같으면: 그대로 연다.
  - N 보다 작으면: 마이그레이션한다.
  - N 보다 크면: 열지 않는다. "이 데이터는 더 새 판의 Jindesk 가 만들었다 · 앱을 업데이트한다"를 보이고, 업데이트 확인을 바로 돌린다.
- 폰 앱은 마이그레이션하지 않는다. 받은 커밋의 스키마 버전이 자기 것과 같을 때만 그 판으로 바꾸고, 다르면 앱을 업데이트하라는 안내를 띄우고 마지막으로 받은 사본을 계속 보인다(`MOBILE.md`). 그래서 스키마를 올리는 릴리즈를 내면 폰 앱도 같은 커밋으로 다시 설치한다.

## 두 가지 마이그레이션

| | 코드 마이그레이션 | 에이전트 마이그레이션 |
|---|---|---|
| 무엇 | 모양 변경. 필드 이름 바꾸기, 파일 쪼개기·합치기, 값 바꾸기, 경로 옮기기 | 의미 변경. 옛 페이지에 주장 장부 붙이기, 가이드가 바뀌어 항목 코드 다시 맞추기, 글 블록 명세를 새 판의 뜻으로 옮기기 |
| 누가 | 앱 번들의 Swift 코드 (`Migration/Step_<n>_<n+1>.swift`) | `migration` 작업. 지침은 `jobs/migration-<n>-<n+1>/INSTRUCTIONS.md` |
| 어디서 쓰나 | 관리자가 Claude Code 로 쓴다. 유연성은 여기서 얻는다 | 학생 맥에서 격리된 `claude -p`로 돈다 |
| 결정적인가 | 그렇다. 같은 입력이면 같은 바이트 | 아니다. 그래서 러너가 결과를 검증한다 |
| 시간과 사용량 | 몇 초 | 대상 수만큼 든다. 사용량 미루기를 따른다 |

한 단계(N → N+1)에 둘이 함께 있을 수 있다. 차례는 코드 → 에이전트 → 코드(뒷정리)다.

**에이전트에 통과시키지 않는 것.** 학생이 쓴 글이다.
- 대상: 코멘트, 메모, 요구의 메모, 확인 문제의 답
- 코드 마이그레이션만 다루고, 바이트 그대로 옮긴다.
- 에이전트 마이그레이션의 입력에서 이 파일들을 뺀다.

**기록은 제자리에서 고치지 않는다.** `records/`, `library/entries/`, `learner/*.jsonl`, `sources/`가 기록이다.
- 기본: 옛 판을 읽는 코드(판마다 디코더)를 남겨 둔다.
- 꼭 모양을 바꿔야 하면: 원본을 `archive/<스키마 버전>/`으로 옮기고 새 모양의 사본을 쓴다(Assayer 의 `catalog/archive`와 같다).

**내용 다시 쓰기는 마이그레이션이 아니다.** 새 작업 지침 때문에 설명을 다시 쓰는 일은 마이그레이션이 아니라 재생성이다. 지침 판이 바뀐 단위는 낡은 것으로 표시되고, 학습 페이지 만들기·번역·부분 다시 만들기가 필요한 단위만 천천히 다시 만든다(`REGENERATION.md`). 업데이트 때 이것을 한꺼번에 돌리지 않는다.

**그림 블록의 코드는 마이그레이션하지 않는다.** 공통 부품은 하위 호환을 지킨다. 깨지는 변경 때문에 옛 부품 판을 쓴 그림 블록이 낡으면, 위와 같이 재생성으로 천천히 다시 만든다(`PAGES.md`의 그림 블록).

## 차례

```
1. 대기열을 멈춘다. 도는 작업이 있으면 끝날 때까지 기다린다 (업데이트는 원래 작업이 없을 때 설치된다)
2. 데이터 폴더 잠금을 잡는다
3. 자동 백업: 앱 지원 폴더의 backups/Jindesk-마이그레이션-<N-1>-<N>.zip (최근 세 개를 둔다)
4. 사본을 만든다: 데이터 폴더 옆의 .Jindesk-migrating-<N>/ (APFS 복제라 공간을 거의 쓰지 않는다)
5. 단계마다 사본에서 돈다: 코드 → 에이전트 → 코드
6. 검증한다 (아래)
7. 바꿔 끼운다: 데이터 폴더 → .Jindesk-before-<N>/, 사본 → 데이터 폴더 (같은 볼륨 안의 이름 바꾸기)
8. meta/schema.yaml 의 history 에 덧붙이고, records/migration/<N-1>-<N>/ 에 계획과 검사 결과를 남긴다
9. 색인을 지우고 다시 만든다
   마이그레이션 결과는 대기열을 연 뒤의 첫 커밋으로 데이터 리포에 올라간다 (사본에도 .git 이 함께 복제되므로 바꿔 끼운 폴더도 그대로 리포다)
10. 다음에 켤 때 문제가 없으면 .Jindesk-before-<N>/ 을 지운다 (백업 zip 은 남는다)
```

- **중간에 꺼지면.** 사본 폴더와 표시 파일(`.Jindesk-migrating-<N>/MIGRATING`)이 남는다.
  - 다음에 켤 때 단계 번호를 보고 이어서 하거나, 사본을 버리고 처음부터 다시 한다.
  - 원래 데이터 폴더는 7 전까지 건드리지 않았으므로 언제나 그대로다.
- **에이전트 단계는 파일마다 결과를 남긴다.** 끊겨도 끝난 파일은 다시 하지 않는다. 실패한 파일만 다시 돌린다.
- **실패하면.** 사본을 버리고 원래 폴더를 그대로 둔다. 앱은 "데이터를 새 모양으로 바꾸지 못했다" 화면을 보이고 두 가지를 고르게 한다. 다시 시도, 이전 판 앱 받기 안내. 그동안은 데이터를 열지 않는다.

## 검증

바꿔 끼우기 전에 사본 전체를 본다. 하나라도 어긋나면 실패다.

| 검사 | 무엇 |
|---|---|
| 스키마 | 모든 파일이 새 버전의 JSON Schema 에 맞는다. 모든 JSONL 줄이 읽힌다 |
| 수 보존 | 자료, 쪽, 엔트리, 개념, 단위, 코멘트, 요구, 확인 문제 기록의 수가 같다. 단계가 늘거나 줄인다고 선언한 것만 다를 수 있다 |
| 학생 글 | 학생이 쓴 글이 바이트 그대로다 (단계 전후의 해시 대조) |
| 기록 | 기록 파일의 해시가 그대로다. 보관으로 옮긴 것은 보관에 원본이 있다 |
| 주장 장부 | 단위마다 주장 수가 줄지 않았다. 출처가 모두 있는 자료 쪽이다 |
| 뜻 해시 | 단계가 뜻을 바꾸지 않는다고 선언한 단위는 뜻 해시(`DATA.md`)가 같다 |
| id | 단위 id, 코멘트의 자리, 요구의 대상이 모두 있는 단위를 가리킨다 |
| 에이전트 결과 | 에이전트 마이그레이션의 출력이 그 단계 스키마에 맞고, 공통 검사(`JOBS.md`)를 통과한다 |

## 관리자가 하는 일

- 마이그레이션 코드는 Claude Code 로 쓴다. 바꿀 모양과 까닭을 적고, 이전 스키마와 새 스키마를 함께 준다.
- **릴리즈 전에 학생의 실제 백업 사본으로 시험한다.**
  - 사본은 학생 맥에서 만든 백업 zip 이다.
  - `jindesk migrate --check <백업 폴더>`: 사본에서 마이그레이션을 돌리고, 검증 결과와 바뀐 파일 목록, 차이를 보인다. 원래 폴더는 건드리지 않는다.
  - 에이전트 단계가 있으면 표본 몇 개만 돌리는 `--sample <n>`으로 비용을 줄인다.
- 마이그레이션 시험은 Assayer 의 `ReplayTests`처럼 둔다.
  - 고정된 옛 데이터 폴더 표본을 시험 자원으로 둔다. 개인 정보가 없는, 관리자가 만든 표본이다.
  - 코드 마이그레이션 결과를 기대 파일과 글자 단위로 견준다.
- 릴리즈 노트에 스키마 버전과 마이그레이션 종류(코드, 코드+에이전트)를 적는다.

## 첫 버전에 넣을 것

1단계부터 있어야 한다. 나중에 붙이면 그때 이미 쌓인 데이터를 다룰 길이 없다.
- `meta/schema.yaml`과 버전 확인
- 파일마다 `kind`와 `v`
- 마이그레이션 실행기의 뼈대: 백업, 사본, 단계, 검증, 바꿔 끼우기, 중간에 꺼졌을 때 이어 하기
- 단계는 하나도 없어도 된다
- `jindesk migrate --check`
